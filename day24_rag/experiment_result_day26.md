# Day 26 實驗結果：串流

跑於 2026-09-21，本機 uvicorn（port 8026，記憶體快取後端），`gpt-4o-mini`。
同一組 28 題（單條文 15 ＋ 多條文 8 ＋ 陷阱 5），跟 Day 20 起用的是同一組。

量測工具 `sse_probe_day26.py`：用 `httpx` 的 stream 模式，
在收到每一行的當下打時間戳。不用 `curl`，因為它會緩衝，量不到第一個 token 的到達時間。

**每一題都是串流與非串流交錯跑**，同一題自己跟自己比。
分兩次跑各自算中位數會被題目難易度洗掉，也會被當下的網路狀況洗掉。

暖機：正式跑之前先送一題不列入統計的。第一次呼叫含 TLS 握手與 openai client
初始化，實測多花 12.8 秒，量進去會把中位數帶歪。

## 冷組：真的打 API（`use_cache=false`），n=28

| | 中位數 | p95 |
| --- | --- | --- |
| 到 `citations` 事件 | **219.2 ms** | 274.8 ms |
| 到第一個 `token` | **850.1 ms** | 1,032.4 ms |
| 到 `done`（總時間） | **1,386.3 ms** | 1,925.8 ms |
| 非串流總時間 | 1,423.1 ms | 2,179.7 ms |

拆開看：

| 段 | 中位數 |
| --- | --- |
| 算向量＋檢索（到 `citations`） | 219.2 ms |
| 模型的 TTFT（`citations` → 第一個 token） | 631.0 ms |
| 生成期間（第一個 token → 最後一個） | 536.2 ms |
| `token` 事件數 | 39 個 |

成對差額（串流 − 非串流）：中位數 **−100.5 ms**，串流較快 **20/28** 題。

## 熱組：快取命中，n=28

| | 中位數 | p95 |
| --- | --- | --- |
| 到 `citations` | 20.9 ms | 25.5 ms |
| 到 `done`（總時間） | **23.5 ms** | 29.1 ms |
| 非串流總時間 | **21.0 ms** | 27.7 ms |

成對差額：中位數 **+2.5 ms**，串流較快只有 **4/28** 題。
串流是非串流的 **1.12 倍**。

### 第 3 條錯在哪

我以為分段送會多出開銷，所以總時間會變長。實測是反過來的：
成對比較下串流在 20/28 題比較快，中位數快 100.5 ms。

可能的機制：非串流要等模型把整段生完、組完、序列化完才開始傳；
串流是邊生邊傳，最後一個 token 一產生就已經在路上了，
`done` 事件緊接著送。也就是傳輸跟生成重疊了。

**這只是合理的解釋，我沒有隔離驗證過。** 要確認的話得分別量
「模型回完整回應的時間」與「模型吐完最後一個 token 的時間」，
今天沒做。寫在這裡是提醒自己那 100 ms 還沒有被證明來自哪裡。

### 反轉候選：方向對，倍數錯

命中時串流確實比較慢，但只慢 1.12 倍不是 2～4 倍。
我高估了分段的開銷——`replay()` 把 31 個字切成兩段送，
多的那一趟在 localhost 上只值 2.5 ms。

結論不變：**串流買到的是「等模型的時候有東西看」。沒在等就沒得買。**
命中率高的場景不該開串流，但代價也遠比我想的小。

## 一個沒預期到的觀察

冷組的答案，串流與非串流只有 **17/28** 完全一致。

兩邊是兩次獨立的 API 呼叫，`temperature=0` 只把隨機性壓到最低，
不保證位元級一致——這件事 Day 18 就寫過，今天又撞到一次。
熱組因為兩邊都讀同一份快取，28/28 一致。

所以「串流版答案會不會不一樣」這個問題，答案是：
**跟串流無關，是呼叫兩次就會不一樣。**
