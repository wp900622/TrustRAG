# Day 17 計畫：多條文綜合題 —— RAG 真正的難關

一句話：**Day 14~16 的題目全部一條條文就答得完，所以那三天量到的 recall
是假的簡單。今天把題目換成「缺一條就算不出來」，看那把尺會裂成什麼樣子。**

Day 15 的 `day15_plan.md` 末尾把三件事留給後面，今天一次收：多條文綜合題、
lost in the middle、reranker。

## 一、今天的新尺：聯集 recall

| 尺 | 定義 | 在單條文題上 | 在多條文題上 |
|---|---|---|---|
| 單條 recall@k | 必要條文中，有幾條進了 top-k | 就是 recall@k 本人 | 會虛高——撈到一半也算 50% |
| **聯集 recall@k** | **所有必要條文都進 top-k 才算命中** | 與上者相同 | 才是答得出來的必要條件 |

Day 15 的結論「答對率天花板 = recall@k」只在單條文前提下成立。
兩條條文時，天花板變成**聯集** recall——而聯集是乘法，不是加法。

## 二、八題（`questions_day17.json`）

每題的 `facts` 刻意跨兩條條文取，缺一條就湊不齊：

| 題號 | 問題 | 必要條文 | fact 來自哪一條 |
|---|---|---|---|
| 301 | 平日加班 3 小時，加班費怎麼算 | 19 + 33 | 三分之一、三分之二（19）／本薪（33） |
| 302 | 補休可以改領加班費嗎？沒排到呢 | 20 + 26 | 變更（20）／六個月、折算（26） |
| 303 | 住宿 3,200 元又掉了發票 | 40 + 42 | 三千元、自行負擔（40）／切結（42） |
| 304 | 曠職三天被解僱，有資遣費嗎 | 32 + 56 | 三日（32）／不發給資遣費（56） |
| 305 | 試用三個月有沒有特休 | 2 + 22 | 比例（2）／六個月、三日（22） |
| 306 | 這個月遲到三次會被記過嗎 | 12 + 46 | 書面提醒（12）／申誡（46） |
| 307 | 東西沒交還可以不發服務證明嗎 | 53 + 57 | 暫緩（53）／七個工作日（57） |
| 308 | 停班改在家上班要不要簽到 | 15 + 16 | 正常出勤（16）／簽到（15） |

301 是 Day 15 用來偷看的那一題，留著當基準線，數字要跟
`experiment_result_multihop.md` 對得上。

挑題原則：**兩條條文的字面相似度要夠低**。第 19 條與第 33 條就是範例——
問「加班費」時第 33 條（薪資結構）一點都不像，所以它 k=10 才擠進來。
兩條長得很像的題目量不到東西，向量檢索本來就會一起撈回來。

## 三、三個對照維度

```
一、k 掃描 1 / 3 / 5 / 10 / 15   → 單條 recall vs 聯集 recall 的裂縫
二、條文順序（固定 k=10）         → 相似度序 / 反序 / 必要條文塞中間
三、rerank 15→3                  → 補得起檢索的落差嗎？帳單多少？
```

**維度二要單獨講清楚**：三組的 context 內容完全一樣，只有順序不同，
輸入 token 幾乎相等。所以那張表比的不是「給了多少資訊」，
而是**同樣的資訊擺在不同位置，模型讀不讀得到**。
如果三組答對率一樣，結論是「這個規模的 context 還沒有 lost in the middle」——
這也是個可以寫的結論，不必硬要有落差。

**維度三的陷阱**：rerank 看起來省 token（只送 3 條進生成），
但它自己要先把 15 條完整讀一遍。候選池的錢一樣要付，只是換一行帳。
報表把重排與生成的 token 分開列，就是為了不讓這件事被藏起來。

## 四、reranker 的作法與它量不到的東西

listwise（整批排序）而非 pointwise（逐條打分），因為 pointwise 看不見
條文之間的**互補性**——而互補性正是今天的主題：第 19 條與第 33 條
單獨看都只有一半。

刻意不用 cross-encoder：本系列不引進要下載 1GB 模型的依賴，
而且 `rag_core.chat()` 已經有快取與雙軌成本統計。代價寫在文章裡：

- 裁判與考生是同一個 `gpt-4o-mini`。它挑不出來的條文，生成時本來也用不好；
  這個實驗量不到「換更強的重排模型會不會更好」。
- 回傳格式靠 prompt 約束，不是 function calling。解析失敗會退回原順序，
  而且報表會把 fallback 次數印出來——不能讓 fallback 混進「reranker 的功勞」。

## 五、招牌表的骨架

```
| k  | 單條 recall | 聯集 recall | 答對率 |
|----|------------|------------|--------|
| 1  |            |            |   /8   |
| 3  |            |            |   /8   |
| 5  |            |            |   /8   |
| 10 |            |            |   /8   |
| 15 |            |            |   /8   |
```

兩欄 recall 的落差就是文章的主圖。預期（跑完要回來對）：
單條 recall 在 k=3 就很好看，聯集 recall 到 k=10 還爬不上去。

下標題等實驗跑完。如果 rerank 把聯集 recall 拉滿，標題往「重排是多條文題的解」
走；如果沒有，往「向量檢索天生問不出互補性」走——後者其實更有意思。

## 六、成本的處理方式

沿用 Day 16 的教訓：`run_experiment_day17.py` 內建 tiktoken 離線重數，
所以不需要再寫一支 `measure_cost.py`。報表同時給兩個數字：

- **本次實際計費**：快取沒命中的部分，重跑會變小甚至 0
- **全部從零跑**：讀者自己跑要付多少
