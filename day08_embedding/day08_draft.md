# [Day 8] 問「特休沒休完會怎樣」，程式怎麼知道要看規章哪一段？

昨天在 Day 7 的結尾，我說 RAG 就像讓 LLM 開卷考：不用死背，考試時翻資料夾找答案。

但今天動手做的時候，我馬上發現開卷考有一個前提——

**你要先翻得到那一頁。**

如果考試時整本課本丟給你，卻不知道答案在第幾章，開卷跟沒開是一樣的。所以進入 Stage 2 的第一步，我刻意先不碰 LLM，也先不裝向量資料庫，只做一件事：

> 給一個問題，程式要能從文件裡找出最相關的段落——而且我要能**量測**它找得準不準，不是看起來會動就好。

這件事用純 Python 就能做出來，程式碼不到百行。

## 一、素材：一份虛構的《員工請假管理規範》

網路上的 RAG 教學九成拿維基百科或英文論文當語料，跑起來很順，但很難代入。我在 Day 1 就說過，企業導入 LLM 第一個撞到的牆是「模型不知道公司內部的資料」——所以我自己造了一份擬真的語料：

**《員工請假管理規範》，共 12 條**：特休天數與申請時程、特休沒休完的遞延與結算、病假診斷證明、補休效期、婚喪假、家庭照顧假、職務代理人、緊急事故補請、曠職處分。

（聲明：內容純屬虛構，不是任何公司的實際規章。）

之後整個系列——Chunking、向量資料庫、一路到 AI Agent——都會用這同一份文件當語料。它夠小、夠真實，而且天生就有陷阱：文件用公文體寫「補休」，但真實的使用者會問「**加班換的假**會不會過期」。這個落差後面會派上用場。

## 二、實作：三步做出最小可用的檢索

### 第 1 步：把文件切成一段一段

今天先用最天真的切法：**一條規定＝一段**，用 Markdown 的 `## ` 標題直接切。

```python
def load_articles(path):
    """把規範文件依「## 第 N 條」切成一條一段"""
    text = Path(path).read_text(encoding="utf-8")
    articles = []
    for block in text.split("\n## ")[1:]:
        lines = block.strip().splitlines()
        title = lines[0].strip()
        body = "\n".join(lines[1:]).strip()
        articles.append({"title": title, "text": f"{title}\n{body}"})
    return articles
```

先說清楚：這個切法能用，是因為這份文件剛好一條一個主題、長度都不長。**這是運氣，不是方法。** 真實文件不會這麼配合——這是明天的主題，今天先欠著。

### 第 2 步：把每一段變成向量

用 OpenAI 的 `text-embedding-3-small`，把 12 條條文一次全部轉成向量：

```python
response = client.embeddings.create(
    model="text-embedding-3-small",
    input=[article["text"] for article in articles],
)
```

呼應 Day 3 講過的觀念：每段文字會變成一個 1536 維的數值向量，**語意越接近的內容，向量距離越近**。「相關不相關」從一個感覺，變成一個可以計算的數字。

這裡我多做了一件後端工程師的反射動作：**算過的向量快取在本機 JSON**，以內容雜湊當 key——文件沒改就不重算，改了哪段就只重算哪段。重跑實驗不重複花錢。

### 第 3 步：問題也轉成向量，算餘弦相似度

```python
def cosine_similarity(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
```

使用者的問題同樣轉成向量，跟 12 條條文一一算相似度，排序取前三名。整個「檢索」就這樣——沒有資料庫、沒有框架，一個 `numpy` 就夠了。

實際跑起來像這樣：

```text
> 特休沒休完會怎樣
  1. [0.xxxx] 第 3 條（特休假之遞延與結算）
  2. [0.xxxx] 第 2 條（特休假）
  3. [0.xxxx] 第 6 條（補休）
```

## 三、這樣做一次，到底花多少錢？

`text-embedding-3-small` 的定價是**每一百萬 token 0.02 美元**。

我把整份規範（12 條）加上 10 個測試問題全部 embedding 一次，實際用量：

- 消耗 token：【待填】tokens

對，你沒看錯，單位是「元」以下。Embedding 是整個 RAG 管線裡最便宜的一環——貴的在後面的 LLM 生成，這個帳之後會算給你看。

## 四、小實驗：10 個問題，實測它找得準不準

demo 會動不代表能用。我設計了 10 個測試問題，刻意分成兩組：

- **5 個直白問法**：用詞跟文件幾乎一樣，例如「婚假總共有幾天？」
- **5 個口語問法**：故意用文件裡**沒出現過的講法**，例如「加班換的假放到過期會怎樣？」（文件寫的是「補休」）、「特休沒休完會怎樣？」（文件寫的是「遞延與結算」）

每題事先標好預期命中的條文，判定標準：**top-1 是不是那一條**。

## 五（版本 A，有題目沒中時用）：沒中的那幾題，才是今天最有價值的部分

把沒命中的題目 top-3 攤開來看：

【待填：貼上 experiment_result.md「沒命中的題目」段落】

問題出在哪？**使用者說的話和文件寫的字，根本是兩種語言。**

文件是公文體：「補休應於加班事實發生日起六個月內休畢」。人是口語：「加班換的假放到過期會怎樣」。兩段文字沒有幾個字重疊，embedding 雖然抓語意不抓字面，但語意的距離還是會被用詞拉開——相似度分數直接反映了這件事。

我今天不解決它。這個坑是之後 query 改寫與 rerank 的主題，先把洞挖在這裡。但我想強調：**如果我只跑一個 happy path demo，我根本不會知道這個問題存在。** 這就是為什麼檢索要量測，不能用感覺驗收。

## 五（版本 B，10 題全中時用）：全中，但我一點都不敢開心

10 題全中，比我預期的好。但把分數攤開看就笑不出來了：

【待填：對比幾題的分數——直白題 top-1 大概 0.6~0.7，口語題 top-1 可能掉到 0.4~0.5，而且跟 top-2 的差距縮小】

直白問法贏得輕鬆，口語問法是**險勝**：top-1 和 top-2 的分數差距明顯縮小。今天語料只有 12 條，選項少所以矇對了；等 Day 9 把真實長度的文件切成幾百段，這種幾個百分點的差距就是命中和沒命中的差別。

換句話說：**demo 全對，不代表方法可靠——它只代表考題太簡單。** 這就是為什麼我堅持每個環節都要留下可以量測的數字，而不是看它會動就過。

## 小結

一句話總結今天：

> Embedding 不是讓程式「看懂」文字，是把「相關不相關」變成可以計算的距離。

而且這個距離量得出來、也量得出**極限**——它會被「使用者的口語」和「文件的公文體」之間的用詞落差拉開。

今天還有一個沒解決的問題：這份文件一條剛好一段，是我運氣好。真實世界的文件是 30 頁的 PDF——切太大會塞爆 context，切太小語意會碎掉。**到底要怎麼切？**
