# [Day 9] 同一份文件、同一組問題：三種切法，命中率差多少？

Day 8 結尾我自己招了：那天的檢索能動，是因為語料剛好一條規定一個主題、每條都短——**一條＝一段能用，是運氣，不是方法**。

今天就把運氣拿掉。文件換成真實長度，然後拿三種切法，用同一組測試問題實測給你看。

結果跟我預期的不一樣。三種切法的**命中率幾乎打平**——但把結果攤開看，它們「命中」的方式完全是三回事。這個差別比命中率本身重要，因為它會直接決定之後你塞給 LLM 的 context 是乾淨的一條規定，還是三百字的大雜燴。

## 一、語料升級：從 12 條變成 59 條

Day 8 的《員工請假管理規範》只有 12 條，切法根本沒有發揮空間。今天把它擴成一份完整的《員工工作規則》：

- **11 章、59 條、全文約一萬字**：總則、聘僱試用、出勤、加班、請假、薪資、差旅、獎懲、資安、離職、附則
- Day 8 那 12 條變成其中的「第五章 請假管理」，內容原封不動、只重編條號——**Day 8 的 10 個測試問題可以直接沿用**，答案還是同樣那幾條
- 我刻意埋了陷阱：有幾條寫得特別長（薪資結構、差旅報支細則），一定會被固定字數切法腰斬；「出勤管理」跟「請假管理」、「資安保密」跟「獎懲」講的事情高度相關，是天然的干擾項

（聲明：內容純屬虛構，不是任何公司的實際規章。）

## 二、三種切法

### 切法一：固定字數硬切

最天真的做法：每 300 字剁一刀，完全不管句子、段落、條文的邊界。

```python
def chunk_fixed(text, size=300):
    chunks = []
    for start in range(0, len(text), size):
        end = min(start + size, len(text))
        chunks.append({"text": text[start:end], "start": start, "end": end})
    return chunks
```

注意每個 chunk 都帶著 `start`/`end`——它在原文中的字元範圍。這不是實作需要，是**實驗需要**，等下判定命中全靠它。

### 切法二：固定字數＋overlap

硬切最明顯的問題是句子被腰斬：「補休應於加班事實發生日起六個月內」在這塊，「休畢」在下一塊。常見的補救是讓相鄰兩塊重疊一段（這裡取 100 字），句子被切斷時，至少有一塊保有完整的上下文。

```python
def chunk_fixed_overlap(text, size=300, overlap=100):
    chunks = []
    step = size - overlap
    for start in range(0, len(text), step):
        end = min(start + size, len(text))
        chunks.append({"text": text[start:end], "start": start, "end": end})
        if end == len(text):
            break
    return chunks
```

### 切法三：依結構切

Day 8 做法的一般化：文件本來就有「## 章、### 條」的結構，就照它的邊界切，一條規定＝一塊。

```python
def chunk_by_structure(text):
    """只保留「### 第 N 條」層級的區塊；章標題與前言不含答案，不進檢索範圍"""
    chunks = []
    for match, start, end in _blocks(text):   # 依 Markdown 標題位置切區段
        if match.group(1) != "###":
            continue
        chunks.append({"text": text[start:end].strip().removeprefix("### "),
                       "start": start, "end": end})
    return chunks
```

三種切法切出來的規模：

| 切法 | chunk 數 | 平均字數 |
|------|---------|---------|
| 固定字數 | 34 | 298 |
| 固定字數+overlap | 51 | 297 |
| 結構化（依條文） | 59 | 161 |

## 三、實驗設計：同一把尺，才能比

測試問題 15 題：**Day 8 的 10 題原封不動沿用**（5 直白＋5 口語，答案都在請假章），再加 5 題打向新章節（加班上限、忘刷卡、住宿報支、洩密處分、離職預告），確認結論不是請假章專屬。

麻煩的是判定標準。Day 8 判「top-1 是不是那一條」，但現在三種切法的邊界都不一樣，固定切法的一塊可能橫跨五條規定，「是不是那一條」根本無從比起。所以改用範圍判定：

> **top-1 chunk 在原文中的字元範圍，是否與預期條文的範圍重疊。**

沾到就算命中——這把尺刻意從寬，而且你等一下會看到，從寬的尺偏袒誰。

## 四、結果：命中率打平，然後呢？

| 切法 | chunk 數 | 沿用10題 | 其中直白 | 其中口語 | 新增5題 | 全部15題 |
|------|---------|---------|---------|---------|--------|---------|
| 固定字數 | 34 | 6/10 | 3/5 | 3/5 | 4/5 | **10/15** |
| 固定字數+overlap | 51 | 6/10 | 3/5 | 3/5 | 3/5 | **9/15** |
| 結構化（依條文） | 59 | 6/10 | 4/5 | 2/5 | 4/5 | **10/15** |

第一眼結論：**切法沒差？** 10、9、10，統計上根本是雜訊。

如果我只看這張表就收工，今天等於白做。往下挖，三件事浮出來。

### 發現一：從寬的尺，偏袒大塊

固定切法的「命中」長這樣（Q1，問診斷證明）：

> Top-1 涵蓋：**第 24～28 條**

一塊 300 字橫跨五條規定，病假、事假、補休、婚假、喪假全在裡面——它當然「沾到」第 24 條，判定命中。但這塊拿去給 LLM 當 context，五分之四是無關內容。

結構化切法的命中則是乾淨的一塊一條：Top-1 就是第 24 條本人，相似度 0.60，比固定切法的 0.51 高一截。

**同樣叫命中，拿到的東西完全不同。** 命中率這個指標天生偏袒大塊——塊越大越容易沾到答案，但「檢索到的內容有多少比例真的有用」（之後會正式介紹這叫 precision）就越慘。切法的代價不會消失，只是從「找不找得到」轉移到「找到的有多髒」。

### 發現二：overlap 不是免費保險，這次還倒貼

我原本預期 overlap 至少不會更差——結果它是三者最低（9/15），還丟了一題固定切法有中的（Q15 離職預告）。

原因攤開看很合理：overlap 讓塊數從 34 暴增到 51，每一塊又都摻了前一塊 100 字的內容。Q15 的答案在第 54 條，但 overlap 製造出好幾塊「一半彈性上班、一半加班申請」的混血塊，其中一塊的語意剛好糊到跟問題有點像，就把正確答案擠下去了。

**overlap 解決的是「句子被腰斬」，付出的是「干擾項變多、每塊語意變糊」。** 它是參數取捨，不是白吃的午餐。

### 發現三：結構化切法，直白題大勝、口語題反而最慘

把沿用的 10 題拆開看，結構化切法是「直白 4/5、口語 2/5」——直白題全場最強（相似度動輒 0.65～0.73），口語題全場最弱。

這不是巧合，是塊的大小在說話：

- **塊小、語意純**：問題用詞跟條文一致時（直白題），一條一塊的向量幾乎是靶心，贏得乾脆
- **塊小、沒有冗餘**：問題用詞跟文件對不上時（口語題），小塊沒有多餘的上下文可以「不小心沾到」，死得也乾脆。大塊反而靠著涵蓋範圍廣，矇到幾題

還有一個照妖鏡案例。Q6「加班換的假放到過期會怎樣？」，答案在第 26 條（補休）。結構化切法的 top-1 卻是第 20 條——一條寫著「補休之效期與屆期結算，**依第五章第 26 條規定辦理**」的條文。它跟第 26 條同分到小數點第四位（0.5985 vs 0.5985），就是排在前面。

**文件內部的交叉引用，會製造出「講到答案關鍵字、但本身不是答案」的假目標。** 這種題切法救不了，先記下來。

### 三種切法都死的兩題

Q9「沒來上班也沒跟任何人講」（答案：曠職）和 Q14「把公司資料傳出去會受什麼處分」（答案：懲處事由），三種切法全滅。

Q9 是 Day 8 就認識的老朋友：使用者的口語跟公文體的「未依本章辦理請假手續而未出勤者」幾乎沒有字面交集，三種切法的 top-1 分數全部掉到 0.47 上下——**切法只能決定怎麼分蛋糕，不能改變蛋糕本身的語意距離**。Q14 更慘，答案在獎懲章第 47 條，但資安章第 50～53 條整章都在講保密，向量全被吸過去。

這兩題是留給之後 query 改寫與 rerank 的坑，Day 8 挖過一次，今天確認：**換切法填不平它**。

## 五、這次花了多少錢

三種切法各建一次索引（34＋51＋59 塊）加上 15 個問題，全部 embedding 一次：

- 消耗 token：40,875 tokens
- 成本：約 0.0008 美元 ≈ **新台幣 0.03 元**

問題向量三種切法共用快取，只算一次。切法實驗這種東西，成本上限根本不在 embedding，在你的耐心。

## 小結

一句話總結今天：

> 切法影響的常常不是「找不找得到」，而是**找到的時候，你手上拿到的是什麼**。

命中率三種切法打平，但固定切法命中時給你 300 字大雜燴，結構化切法給你乾淨的一條規定——下一步要把檢索結果塞進 prompt 的時候，這個差別就是生死。而 overlap 示範了另一件事：每個「常識性的最佳實踐」都有代價，不實測你不會知道代價這次站在哪邊。

今天也留下兩個切法解決不了的問題：口語與公文體的用詞鴻溝、交叉引用製造的假目標。這些坑先標好位置，之後回來填。
